# TypeScript AST codegen tooling (Wayfinder #25)

Which mechanism should the v2 generator use to emit TypeScript programmatically —
`ts-morph`, the TypeScript compiler factory API, or a structured-emit
alternative? Judged on deterministic byte-stable output, TypeScript 7 (tsgo)
compatibility, Bun compatibility, ergonomics for schema-heavy Effect code, and
formatting strategy (emit-then-oxfmt).

## Recommendation

**Adopt `code-block-writer` as the emit engine, keep `emit-then-oxfmt` as the
formatting/normalization stage, and keep the `ts.factory` + `ts.createPrinter`
route (with `typescript` pinned as a codegen-time-only devDependency) on the
shelf as the escalation path if we later need guaranteed-valid-AST output.**

Reasoning in one paragraph: both incumbents that already succeed at exactly this
task — this fork's own `packages/core/scripts/generate-openapi.ts` and Effect's
own `@effect/openapi-generator` — emit with **plain strings**, not an AST, and
lean on a downstream formatter. That is strong evidence that a full AST is not
required to produce correct, schema-heavy Effect code. The real pain in the
current fork generator is not "we lack an AST", it is manual `${indent}` and
brace bookkeeping across 2,725 lines. `code-block-writer` removes exactly that
pain (indentation/brace/scope management) while staying a pure string writer with
**zero** compiler-API surface — so it is immune to the TypeScript 7 programmatic-
API churn, trivially Bun-compatible, and deterministic by construction. It is
also the writer that lives *inside* `ts-morph`, so it is battle-tested and
maintained by the same author (dsherret). We get ~80% of ts-morph's ergonomics
for none of its risk.

## What the emitter must express

Sampled from `packages/erebor/src/operations/*.ts` (generated by
`packages/core/scripts/generate-openapi.ts`, delegated to from each package's
`scripts/generate.ts`). Every operation file emits:

- A **dual declaration**: a TS `interface` *and* a same-named `const` Effect
  `Schema.Struct(...)` value (declaration merging), for both Input and Output.
- **Trait annotations** as pipe chains: `.pipe(T.PathParam())`,
  `.pipe(T.HttpHeader("Erebor-Version"))`, `.pipe(T.Http({ method, path }))`.
- **Tree-shaking pragmas** as *leading* comments: `/*@__PURE__*/ /*#__PURE__*/`
  before each `Schema.Struct` and before the `API.make(...)` call.
- **Double casts**: `... as unknown as GeneratedStructCodec<Name>`.
- **Per-operation error unions**: a named import from `../errors.ts`
  (`{ BadRequest, NotFound, Conflict }`) surfaced as `errors: [...] as const`.
- **An operation factory**: `export const op = API.make(() => ({ inputSchema,
  outputSchema, errors }))`.
- **JSDoc** synthesized from OpenAPI `summary`/`description`/parameter docs.
- Deeply **nested inline structs** (address objects, record maps, null-unions).

Two of these constructs — the *leading* `/*@__PURE__*/` comments and the
`.pipe(...)` chains — are precisely the constructs that are awkward to express
through `ts.factory` (leading comments require `ts.addSyntheticLeadingComment`
plumbing per-node; pipe chains become deeply nested `createCallExpression`
trees). They are trivial `.write(...)` calls in a string-writer model. This is
the single biggest ergonomics signal in favor of a writer over an AST factory
for *this* codebase.

## Precedent

- **This fork (incumbent):** `packages/core/scripts/generate-openapi.ts` — 2,725
  lines of manual string concatenation with hand-tracked `indent` parameters
  (`lines.push(\`${indent}  ${key}: ${schema},\`)`). No AST library. Formatting
  is a *post* step: every package's `generate` npm script is
  `bun run scripts/generate.ts && oxlint --fix src && oxfmt --write src && oxfmt --write src`.
  Note the **doubled** `oxfmt --write` — the generated output is not a formatter
  fixpoint in a single pass, which is a determinism caveat (see below).
- **Effect itself:** `@effect/openapi-generator` (in `repos/effect-v4/packages/
  tools/openapi-generator`, v4.0.0-beta.98) emits with `String.stripMargin`
  template literals and **prints to stdout**, leaving formatting entirely to the
  consumer. It has **no** `ts-morph` and **no** `typescript`-factory dependency
  for emit (its only runtime dep is `swagger2openapi`). Effect's `packages/tools`
  also ships `oxc` (custom oxlint rules) and `ai-codegen`, none of which emit via
  AST. In other words, the Effect ecosystem's own answer to "how do we generate
  schema-heavy Effect code" is string templates + external formatting.

The precedent is unambiguous: neither the fork nor Effect reaches for an AST to
emit this shape of code.

## Candidate tradeoff table

| Candidate | Byte-stable output | TS7 / tsgo compat | Bun compat | Ergonomics (schema-heavy Effect) | Formatting fit |
|---|---|---|---|---|---|
| **Raw string templates** (status quo, and Effect's approach) | Yes, if input ordering is stable; whitespace normalized by oxfmt | Total non-issue — no compiler-API surface | Perfect (pure JS) | Poor — manual indent/brace bookkeeping; easy to emit invalid syntax; already the fork's pain point | emit-then-oxfmt (already in use) |
| **`code-block-writer` (recommended)** v13 | Deterministic by construction; oxfmt as safety net | Total non-issue — pure string writer, no compiler API | Perfect (pure TS, zero native deps) | Good — `.block()`/`.indent()`/conditional writers remove indent bookkeeping; PURE comments, pipe chains, casts are plain `.write()` | emit-then-oxfmt; writer can also self-manage most whitespace |
| **`ts.factory` + `ts.createPrinter`** (pin `typescript@5.x`/`6.x` codegen-only devDep) | Deterministic; printer output is ugly but oxfmt normalizes it | Works **only** via the pinned legacy `typescript` package; tsgo exposes **no** stable emit API (see below). Microsoft's own recommended workaround. | Perfect (pure JS) | Fair→poor — guarantees valid syntax, but punishingly verbose for pipe chains, leading PURE comments, and double casts; would grow the emitter substantially | emit-then-oxfmt (printer output must be reformatted) |
| **`ts-morph`** v28 | Deterministic; uses code-block-writer under the hood | **Uncertain but decoupled** — bundles its *own* pinned TypeScript (`@ts-morph/common`), so it does not depend on the project's tsgo; maintainer is pessimistic about a native-compiler future (below) | Good (pure JS + code-block-writer) | Good, but its headline powers (type-info-driven refactoring, find-references) are **wasted** on greenfield emit — you would mostly be driving its embedded code-block-writer anyway | emit-then-oxfmt |
| **`ts-poet`** v6.12 | Deterministic; formats via bundled `dprint-node` | Non-issue for emit (no compiler API) | **Risk** — depends on `dprint-node`, a native (napi/Rust) addon; native addons are the usual Bun sharp edge and add a second formatter alongside oxfmt | Good — auto-organizes/dedupes imports (a genuine win for cross-referencing schema files) | Conflicts — brings its own dprint; we would fight it or bypass it to keep oxfmt as the single source of truth |

## The tsgo / TypeScript 7 programmatic-API claim — VERIFIED

The ticket's caution is correct. TypeScript 7 went GA on 2026-07-08 (RC
2026-06-18). The Go-native compiler (tsgo / "Corsa") **does not** expose a stable
programmatic compiler API in 7.0; it is deferred to 7.1.

- Microsoft's own December 2025 progress post states: "Corsa/TypeScript 7.0 will
  not support the existing Strada API. The Corsa API is still a work in progress,
  and no stable tooling integration exists for it." Its recommended interim
  workaround is to install `typescript` and `@typescript/native-preview`
  side-by-side and "use the ≤6.0 API for tooling that needs it, with `tsgo` for
  type-checking."
  (<https://devblogs.microsoft.com/typescript/progress-on-typescript-7-december-2025/>)
- This validates the ticket's proposed mitigation exactly: **any** compiler-API-
  based emitter (`ts.factory`, or `ts-morph` if it ever tracks the native
  compiler) must run against a pinned legacy `typescript` package used *only* at
  codegen time, while `tsgo` does the repo's actual type checking. The two never
  have to agree on API surface because the pinned `typescript` never type-checks
  the project — it only prints strings.
- `ts-morph`'s maintainer (dsherret), on the native-compiler transition:
  "I don't think ts-morph will continue to exist because the API sounds like it
  will be limited and require IPC ... for ts-morph I think it will be too much
  effort to make something like it continue to work, be slow, and also it will no
  longer work in the browser." (<https://github.com/dsherret/ts-morph/issues/1621>,
  2025-03). Counterpoint from the typescript-go team: "We love ts-morph; it is
  explicitly an anti-goal to prevent ts-morph from working altogether."
  (<https://github.com/microsoft/typescript-go/discussions/455#discussioncomment-12492538>)
- Practical consequence: **the recommended `code-block-writer` avoids this entire
  question** because it touches no compiler API at all. tsgo can be the repo's
  sole type checker (`tsc` → `tsgo`) with zero interaction with the emitter.

## Determinism plan

Emitter choice is **not** the main determinism lever — every candidate is
deterministic given deterministic input. The plan therefore governs the pipeline
around the emitter:

1. **Stable ordering of everything iterated.** Sort OpenAPI paths, then methods
   (fixed `["get","post","put","patch","delete"]` order), operations, schema
   `properties`, `required`, error status codes, and enum members by a total,
   name-based order before emitting. Never iterate a `Map`/`Set`/`Object.keys`
   in insertion order; never let spec authoring order leak into output.
2. **Stable imports.** Collect imports into a sorted, de-duplicated set and emit
   them in a fixed grouping (external → `@distilled.cloud/*` → relative), so
   adding one error type does not reshuffle the import block. (This is the one
   place `ts-poet`/`ts-morph` add value; with `code-block-writer` it is ~30 lines
   of a sorted collector.)
3. **Deterministic names.** Keep the existing collision-suffixing
   (`Name`, `Name2`, ...) but derive it from sorted input so the suffix is stable
   run-to-run.
4. **No nondeterministic inputs in emit.** No timestamps, no RNG, no absolute
   paths, no environment-dependent values baked into output.
5. **Formatting to a fixpoint.** Keep `emit-then-oxfmt`, but treat oxfmt as a
   *normalizer* so the emitter never has to be whitespace-perfect. Run oxfmt to a
   fixpoint (the current scripts already run it twice — encode this as "format
   until stable, max N passes" rather than a magic double-invocation) and, in CI,
   assert `oxfmt --check` is clean and `git diff --exit-code` is empty after
   `generate`, so byte-drift fails the build.
6. **Golden-file tests.** Snapshot a representative set of generated operation
   files; regenerate in CI and diff. This catches emitter nondeterminism and
   formatter drift regardless of which emitter is chosen.

Byte-stability reduces to: *stable ordering + stable content + formatter
fixpoint*. Whitespace stability is delegated to oxfmt, which is why a string
writer is sufficient.

## Risks and mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| String/writer emitter produces syntactically invalid TS (unbalanced generics, missing comma) | Medium | Golden-file + a post-generate `tsgo`/`tsc --noEmit` gate over `src/operations` in CI; escalate specific hostile constructs to `ts.factory` helpers if they recur |
| oxfmt output not a single-pass fixpoint (already observed — scripts run it twice) | High (observed) | Encode format-to-fixpoint loop; `oxfmt --check` + `git diff --exit-code` gate in CI; pin the oxfmt version |
| Chosen emitter later needs real type information (e.g. cross-file inference) | Low | Only `ts-morph` offers that, and it bundles its own TS; adopting it later is additive — `code-block-writer` output can coexist |
| oxfmt version bump silently reflows all generated files | Medium | Pin oxfmt/oxlint versions; treat a formatter bump as an intentional, reviewed regeneration commit |
| tsgo has no stable emit API (7.0) and slips further | High (confirmed for 7.0; 7.1 pending) | Recommended path touches no compiler API, so unaffected; the `ts.factory` fallback is insulated by the codegen-only `typescript@5.x`/`6.x` pin per Microsoft's own guidance |
| `ts-poet`'s native `dprint-node` addon misbehaves under Bun | Medium | Avoided by not selecting ts-poet; its only unique benefit (import organization) is reproduced by the sorted-import collector in the determinism plan |
| Determinism regressions from spec-authoring-order leakage | Medium | Total-order sort of all iterated collections (plan item 1) + golden-file diffing |
